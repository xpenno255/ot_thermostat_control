## How to operate it

- HACS does not notice a new GitHub release by itself for hours. Force it over the websocket:
  `hacs/repositories/list` → find the repo id → `hacs/repository/refresh` → then
  `update.install` on `update.ot_thermostat_control_update`, then `homeassistant.restart`.
- Hub/room options can be set headlessly: `POST /api/config/config_entries/options/flow {"handler": <entry_id>}`
  then `POST .../flow/<flow_id>` with the form, sections nested (`sources_section`, `comfort_section`, …).
  Saving hub options reloads every room.
- History API timestamps are UTC; the owner is on BST/GMT. Convert before reporting.
- Per-room state: `sensor.ot_<room>_state` (attributes: reason, action, fallbacks, geometry_warnings),
  `_would_write`, `_target_ot` (attributes: schedule_source, adaptive_shift, occupancy_offset), `_offset`
  (attributes: physical, trusted, asymmetry, capped, sum_l, solar_k). Hub: running mean, flow temp used.
- To let a room write: `select.ot_<room>_mode` → `active`. Owner must first raise the evohome schedules
  back to true comfort values (v1 habit was to set them 1–2 °C low).

## Known behaviour and gotchas

- First cycle at HA startup runs before evohome/ramses are up → `no_data`, then a 60 s retry recovers
  (fixed in 2.0.3; the callback must be `@callback` or HA runs it in the executor).
- Evohome cloud lags the zone by minutes at switchpoints; 2.0.4 treats a zone already at the next
  switchpoint value as scheduled and promotes the next value once its time has passed.
- `climate.living_room_2` (ramses) occasionally goes `unknown` for a few minutes; air temp falls back.
- Kitchen `would_write` 10.0 means the bifold contact is open (window override); kitchen door contact
  (to the hall) triggers `door_open` = plain schedule target.
- Offline: schedule falls back to ramses zone schedule (RF fetch daily, cached), outdoor to a 6 h cache.
- Hub sensors are push-updated from `OTHubData` listeners (2.0.5).
